# 寫入操作規範（Write Contract）

> 定案 2026-07-19（user 拍板）。這是寫死進系統的契約：**寫入走窄門，查詢維持寬鬆**。
> 目的：把「無窮亂打法 × 缺要素 × ctx 狀態」的組合爆炸，收成一道統一閘門，
> 從源頭消滅「訪客以為成功、其實系統理解錯」的危險級破口。

## 核心原則

| 類別 | 手感 | 理由 |
|---|---|---|
| **查詢類**（庫存/警示/熱銷/到期/連帶/進出/比較） | 寬鬆：口語、亂序、追問都盡量答；追問靠 ctx 補全 | 查錯了訪客看得出來，重問即可，無副作用 |
| **寫入類**（進/出/調貨、改安全庫存、建/刪） | 窄門：三要素齊才開卡，缺就 clarify 補問，**絕不用 ctx 頂替** | 寫錯會落地改資料，訪客可能沒發現 |
| **搗蛋類**（注入/破壞/離題） | 直接拒，不進 clarify | 蓄意破壞，有明確特徵 |

## 鐵律（不可違反）

1. **寫入句絕不用 ctx last_sku/預設倉頂替**。抽不到明確商品/數量/倉別 → clarify 只問缺的那項。
   - 這條是 r77（耳機頂替保溫瓶寫入）、r80（調貨缺商品）危險級的根因修法。
2. **查詢追問維持 ctx 補全**（「它還剩多少」「第二名剩多少」）——鐵律只管寫入。
3. **確認卡是唯一寫入放行路徑**。任何 done 前必經 movement_confirm / transfer_confirm /
   config_confirm / item_confirm 等，且卡片內容 = 抽到的三要素原值。

## 五種寫入操作的標準路線

### ① 進貨 / 出貨 → create_movement
- **完整格式**：`〔倉別〕〔進|出〕〔數量〕〔商品〕`　例：「北倉進50個滑鼠」「南倉出400衛生紙」
- **三要素**：商品 ＋ 數量 ＋ 倉別
- 量詞可省（「出400」= 400 件），數字必須明確
- 缺要素 → clarify：缺商品問商品、缺數量問數量、缺倉問倉（列可選倉）
- 比例語（全出/一半/全部）→ 拒絕換算，要求確切數字
- 負數 / 0 → 擋

### ② 調貨 → create_transfer
- **完整格式**：`〔來源倉〕調〔數量〕〔商品〕到〔目標倉〕`　例：「北倉調30個耳機到南倉」
- **三要素**：商品 ＋ 數量 ＋ 兩倉（來源＋目標）
- 缺商品 → clarify 問商品；缺目標倉 → 問調去哪；只有一倉 → 問另一倉

### ③ 改安全庫存 → manage_config(set)
- **完整格式**：`〔倉別〕〔商品〕安全庫存改成〔N〕`　例：「北倉衛生紙安全庫存改成150」
- 「改回原本」→ 誠實說不記舊值、請給數字（audit log 有歷史）

### ④ 建立商品 → create_item（多步引導）
- 步驟：名稱 → 類別 → 單價+安全庫存 → 初始庫存 → 確認
- 每步驗證：空名/非類別/無數字 → 留步重問；commit 端空名拒絕

### ⑤ 建 / 刪 排程·警示 → set_schedule / set_alert / delete_*
- 刪除走「列表 → 選 ID / 序數 / 剛設的那個」，不猜

## 搗蛋直接拒（黑名單，不進 clarify）
- 注入：`sudo` `rm -rf` `忽略指令` `system prompt` `drop table`
- 破壞：`全部刪掉` `歸零` `改成0元` `1元` `免費送` `白拿`
- 離題閒聊：笑話 / 感情 / 歐巴 / 政治 / 天氣 / 股票

## 實作落點
- **寫入三要素閘門**：所有寫入 dispatch 最前面的統一切面，取代散落各處的補 ctx 邏輯。
- 流程：偵測寫入句 → 抽三要素 → 齊則開卡、缺則 clarify 補問（不猜）→ 搗蛋特徵則拒。

## 自動化守護（r82）
本契約由 `context_fuzz.py` 的 **write_contract_fuzz** 段機器化守護，每輪必跑：
- 29 句 × 六類鐵律（full 開卡／miss 追問／nf 查無不頂替／sab 搗蛋拒／lim 比例負數擋／typo 漏打字纠錯）
- FAIL = 契約違反（CI 擋）；WARN = 可更好但不危險（人工回看）
- 單獨跑：`python context_fuzz.py --rpi5 --only write`
- 新增寫入操作或契約規則時，同步在 `WRITE_CASES` 補測試句。
